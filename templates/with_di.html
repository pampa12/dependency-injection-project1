FINAL PRESENTATION DEMO

See Dependency Injection happen step by step

We are not only showing the checkout result. This demo shows the problem, the dependency being selected, the injection, the checkout, and the testing benefit.

STEP 1

Start with the problem: tight coupling

Without DI

In the tightly coupled version, OrderService creates CreditCardPayment itself. That means OrderService is stuck with one payment type.

Tightly coupled
class TightlyCoupledOrderService:
    def __init__(self):
        self.payment_processor = CreditCardPayment()

To switch to PayPal, we would have to edit OrderService.

OrderService
locked to →
CreditCardPayment
Only one payment choice

What to say: “This is the problem DI solves. The service is creating its own dependency.”

STEP 2

Choose the dependency outside OrderService

Outside the service

Now the payment object is created outside OrderService. Pick one below and watch the live system update.

Selected class CreditCardPayment

What to say: “The payment object is chosen outside OrderService. That is important.”

STEP 3

Inject the payment object into OrderService

Constructor injection
CreditCardPayment
→
receives dependency OrderService
Constructor injection
payment = CreditCardPayment("1234")
service = OrderService(payment)
This line is the injection: OrderService(payment)

What to say: “The dependency is passed into the OrderService constructor instead of being created inside it.”

STEP 5

Show the two biggest benefits: testing and extension

Why DI matters
A

Test without a real payment provider

Inject FakePayment and verify the amount without charging a card or contacting PayPal.

fake = FakePayment()
service = OrderService(fake)
service.checkout(order)
Not run yet
B

Add a new payment type

We added ApplePayPayment without changing the OrderService class.

class ApplePayPayment:
    def pay(self, amount):
        ...

service = OrderService(
    ApplePayPayment()
)
OrderService stays untouched
Final takeaway The dependency changes. OrderService does not.

What to say: “This is why DI is useful in real systems: easier testing and easier replacement of implementations.”
